# Positioning One-Pager

## AI Access & Governance Infrastructure

### Category

This product should be positioned as `AI Access & Governance Infrastructure`.

It is not a token reseller, a chat wrapper, or a lightweight proxy dashboard.

It is the control plane that lets teams adopt Claude Code, OpenAI-compatible tools, and private model routes with the operational discipline they already expect from cloud infrastructure.

### One-line positioning

Give engineering, platform, security, and finance teams one governed layer for AI access, routing, budgets, auditability, and deployment control.

### Core problem

Teams do not just need an API key.

They need a safe, observable, auditable, and billable way to run AI tools across multiple users, projects, environments, and providers without pushing raw provider credentials to every operator.

### What the product does

- Centralizes AI access behind one governed gateway
- Supports BYOK provider connections instead of default token resale
- Issues virtual keys for teams, projects, and environments
- Applies budgets, routing rules, permissions, and usage controls
- Captures logs, exports, and audit evidence for operations and finance
- Supports Cloud first while giving enterprise buyers a path to Hybrid and Self-host Preview

### What makes it valuable

#### For engineering teams

- faster tool onboarding
- one consistent access path across providers
- no need to distribute raw upstream credentials to every developer

#### For platform and security teams

- enforce routing, policy, and access boundaries
- isolate projects and environments
- maintain clearer audit trails and operational ownership

#### For finance and operations

- usage visibility by workspace, project, user, and provider
- budget controls and alerts
- exports for reconciliation, reporting, and customer handoff

### Deep-user experience principles

The product experience should feel good for teams who use it every week, not only for first-demo buyers.

- health checks, route defaults, and handoff evidence should feel like one workflow
- private model support should read as named operating lanes, not raw endpoint trivia
- moving from Cloud to Hybrid should not force operators to relearn the control model
- the next action should be obvious before an operator opens a lower-level screen

### Why this is not "just a proxy"

The gateway is only one piece of the product.

The real value is the combination of:

- control plane
- governance workflows
- credential abstraction
- cost management
- operational evidence
- enterprise delivery posture

That is why the product should be described as infrastructure, not tooling glue.

### Best-fit buyers

- AI-native engineering teams scaling Claude Code or similar tools
- platform teams standardizing AI usage across multiple projects
- agencies or multi-client teams that need isolation and chargeback
- enterprise IT or security teams that need clearer deployment and boundary stories

### Standard language to use

- `AI Access & Governance Infrastructure`
- `Control Plane / Operations Console`
- `BYOK routing with governance controls`
- `Virtual keys, budgets, audit logs, and exports`
- `Cloud first with Hybrid and Self-host Preview paths`

### Language to avoid

- token resale platform
- proxy dashboard
- AI chat site
- model marketplace
- self-hosted enterprise product by default

### Short pitch

This is the governed infrastructure layer for teams using AI coding tools. It gives operators one control plane for access, routing, budgets, logs, exports, and deployment posture so AI usage can scale like any other enterprise system.
