# Deployment Guide

## Supported delivery paths today

### Local developer workflow

Use this when iterating quickly in source mode.

```bash
cp .env.development.example .env.development
npm run env:check
npm run db:up
npm run db:migrate
npm run demo:seed
npm run dev:control-api
npm run dev:export-worker
npm run dev:gateway
npm run dev:web-admin
```

`npm run demo:seed` also writes:

- `.demo/demo-state.json`: machine-readable manifest with seeded ids and tokens
- `.demo/demo-brief.md`: operator-friendly handoff brief with URLs, sample curls, and demo storyline

### Docker demo stack

Use this when showing a pilot environment or handing the stack to another teammate.

```bash
npm run demo:up
```

This stack:

- starts Postgres and Valkey
- runs migrations
- seeds demo data
- launches `control-api`, `export-worker`, `gateway`, and `web-admin`
- prints the generated demo brief to the `seed` container logs

Stop it with:

```bash
npm run demo:down
```

### Preview runtime stack

Use this when you need a production-mode runtime shape for Self-host Preview or enterprise pilot validation.

```bash
cp .env.production.example .env.production
npm run env:check:prod
npm run preview:up
```

This stack:

- builds the multi-stage runtime image from [infra/Dockerfile.runtime](../infra/Dockerfile.runtime)
- runs `control-api`, `gateway`, and `export-worker` from compiled `dist` outputs
- runs `web-admin` through `next start`
- adds container health checks for all application services
- keeps Postgres, Valkey, and export storage on named volumes

Stop it with:

```bash
npm run preview:down
```

Follow these docs when using the preview stack:

- [Self-Host Preview Install Guide](./SELF_HOST_PREVIEW_INSTALL.md)
- [Environment Matrix](./ENV_MATRIX.md)
- [Observability Baseline](./OBSERVABILITY_BASELINE.md)
- [Upgrade and Rollback Runbook](./UPGRADE_ROLLBACK_RUNBOOK.md)

For production OIDC or pilot SSO validation, prefer a stable external `https://` origin for `WEB_ADMIN_BASE_URL`. Temporary tunnel domains can be used for validation, but they are more likely to introduce browser or callback friction than a stable domain.

## Service ports

- `web-admin`: `3001`
- `control-api`: `4001`
- `gateway`: `4002`

The Docker demo stack does not publish Postgres or Valkey to the host. That avoids conflicts with a developer already running `npm run db:up` locally.

## Required env vars

### Shared

- `DATABASE_URL`
- `VALKEY_URL`
- `ENCRYPTION_KEY_BASE64`
- `EXPORT_JOBS_DIR` when `control-api` and `export-worker` do not share a filesystem

### Control API

- `CONTROL_API_HOST`
- `CONTROL_API_PORT`
- `CONTROL_API_ADMIN_TOKEN`
- `EXPORT_JOBS_DIR` should point at the same shared directory used by `export-worker`

### Export worker

- `DATABASE_URL`
- `VALKEY_URL`
- `ENCRYPTION_KEY_BASE64`
- `EXPORT_JOBS_DIR` should point at the same shared directory used by `control-api`
- `EXPORT_JOB_STALE_AFTER_MS` optional override for when a `running` export should be re-queued after worker failure
- `EXPORT_JOB_CLEANUP_INTERVAL_MS` optional override for how often orphaned local export files are pruned

### Gateway

- `GATEWAY_HOST`
- `GATEWAY_PORT`
- `GATEWAY_PUBLIC_BASE_URL`
- `DEMO_MODE`

### Web admin

- `WEB_ADMIN_PORT`
- `WEB_ADMIN_BASE_URL` when OIDC/session login is enabled
- `CONTROL_API_BASE_URL`
- `NEXT_PUBLIC_CONTROL_API_BASE_URL`
- `CONTROL_API_ADMIN_TOKEN`

## Runtime note

The packaged demo stack currently runs:

- `control-api` through its `tsx` start script
- `export-worker` through its `tsx` start script
- `gateway` through its `tsx` start script
- `web-admin` through `next dev`

This keeps the monorepo source-first workflow intact while still giving us a repeatable demo/self-host bring-up path.

That is acceptable for demo delivery. Customer-facing preview work should move to the preview runtime stack instead of the demo stack.

Export downloads are generated by `export-worker` and served by `control-api`, so split-process or split-container deployments must mount the same `EXPORT_JOBS_DIR` into both services.

The worker automatically re-queues stale `running` jobs and removes orphaned files from `EXPORT_JOBS_DIR`, but it does not delete files that are still referenced by completed export jobs.

## Operational recommendation

For any customer-facing environment:

- rotate `CONTROL_API_ADMIN_TOKEN`
- rotate `ENCRYPTION_KEY_BASE64`
- set `DEMO_MODE=0` once real provider keys are configured
- replace the seeded demo org/workspaces with real tenant data
- remove or replace any active seeded provider connections that still use placeholder credentials such as `demo-openai-key`
- align commercial promises with [Delivery Matrix](./DELIVERY_MATRIX.md)
- use the health checks described in [Observability Baseline](./OBSERVABILITY_BASELINE.md)

## Env file policy

- Development and demo commands load `.env.development.local` first, then `.env.development`.
- Preview and production commands load `.env.production.local` first, then `.env.production`.
- Runtime commands no longer read root `.env` or `.env.local`.
